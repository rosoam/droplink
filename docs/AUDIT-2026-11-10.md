## P0 — bloquant fonctionnel

### 1. Le drag & drop est cassé — aucun moyen d'envoyer un fichier
`src/components/DropZone.tsx:52-58` lit `file.path`. Tauri v2 a supprimé `File.path` (API v1) ; les chemins arrivent par
`getCurrentWebview().onDragDropEvent` (`node_modules/@tauri-apps/api/webview.d.ts:22-33`). Le `@ts-expect-error` masque
l'erreur. En plus, avec `dragDropEnabled` par défaut (true), la WebView intercepte l'événement OS et les handlers HTML5
`onDrop` ne se déclenchent pas. Résultat : `paths` reste vide, `onFilesDropped` n'est jamais appelé.
Il n'existe aucun sélecteur de fichier de secours (`tauri-plugin-dialog` est installé mais jamais appelé).
**C'est la seule voie d'envoi de l'app.**

### 2. Le relay ne transfère rien — cross-réseau impossible
`relay_client.rs` enregistre le pair et reçoit `RoomUpdate`. `transfer.rs:291` fait uniquement
`TcpStream::connect(device.ip:port)` sur l'IP **privée** annoncée. Deux appareils derrière deux NAT différents se voient
dans la liste et **tout envoi échoue**. Le README et le plan v2 annoncent « relayed via WebSocket » : ce chemin de données
n'existe pas.

### 3. « Transfert terminé » est un mensonge côté émetteur
`transfer.rs:357-365` émet `Complete` dès la dernière écriture socket, sans ACK du récepteur. Si le checksum échoue en
face, l'émetteur affiche quand même ✓. Aucun `Message::Done`/`Error` en retour.

### 4. Le débit réseau est couplé au renderer
`transfer.rs:217` et `:347` font `event_tx.send(Progress).await` **par chunk de 64 KiB**. 1 Gio = 16 384 événements IPC
sérialisés, chacun attendu par la boucle de transfert. Sur fichier volumineux, la vitesse d'envoi devient la vitesse
d'affichage de la WebView.

### 5. Multi-fichiers cassé
`App.tsx:16-22` lance tous les fichiers en parallèle ; `useTransfer.ts` ne garde qu'un `activeTransfer` et un
`currentFileNameRef` global → les événements de N transferts s'écrasent, le nom affiché est faux, un seul transfert
visible.

### 6. Identité des appareils incohérente
Registre clefé `ip:port` (`device_registry.rs:117`), frontend dédupliqué par `name` (`useDevices.ts:15`), `device-lost`
émet un `name` et retire **tous** les homonymes. Deux « MacBook Pro » sur le réseau = un seul affiché, retrait aléatoire.
Le mapping `fullname_to_id` de `main.rs:96-118` approxime le fullname mDNS par `"{name}."` et fuit une entrée à chaque
perte non résolue.

### 7. Découverte morte sur réseau isolé
`get_local_ip()` (`discovery.rs:106-110`) passe par une route UDP vers `8.8.8.8`. Sans route par défaut — le cas d'usage
« LAN sans internet » — retour `None`, puis `127.0.0.1` (`main.rs:70`), puis advertisement mDNS sur loopback : personne ne
te voit. Il faut énumérer les interfaces et choisir une IPv4 privée.

### 8. Courses et collisions d'écriture
- Port : `find_free_port` bind puis drop, `TransferServer` re-bind plus tard (`main.rs:75-82`) — TOCTOU ; `.expect()` si
  aucun port libre.
- Fichier : `unique_path()` teste `exists()` puis `File::create` (`transfer.rs:181-194`) — deux réceptions simultanées du
  même nom s'écrasent. Il faut `OpenOptions::create_new`.

### 9. Aucune borne sur l'entrant
`TransferServer::start` accepte un nombre illimité de connexions (`transfer.rs:67-75`), aucune limite de taille disque, de
connexions simultanées ou de débit. Un pair du LAN peut remplir le disque.

## Goulots d'étranglement (mesurés dans le code)

1. **Double lecture complète du fichier** avant envoi pour calculer le SHA-256 (`transfer.rs:274-288`) : 2× l'I/O disque,
   et donc 2× le temps avant que le premier octet parte.
2. **SHA-256** là où BLAKE3 donnerait 5–10× sur Apple Silicon, avec hachage parallèle.
3. **64 KiB + `BufReader` par-dessus `TcpStream` + `BufWriter`** : triple copie inutile pour des buffers de 64 KiB.
4. **Un événement `Progress` par chunk**, en `send().await`.
5. **`DeviceRegistry`** : `Vec` scanné linéairement + `HashMap` secondaire, deux structures à garder cohérentes.
6. **Allocation d'un buffer 64 KiB par connexion**, sans pool.

## Ce qui est bon et doit survivre

- Le protocole JSON newline-delimited est simple et lisible ; les tests de roundtrip existent.
- `DeviceRegistry` multi-sources (mDNS/Relay/BLE) est la bonne idée — l'implémentation doit juste changer de structure.
- La séparation `protocol / discovery / transfer / tray` est saine.
- L'UI actuelle (Tailwind, dark, 320×500) est propre et cohérente.
- Le serveur relay axum est court et lisible.

## Cible recommandée

Un **workspace Cargo** avec le cœur testable isolé de l'UI :

```
droplink/
├── Cargo.toml                  # [workspace]
├── crates/
│   ├── droplink-core/          # protocole, framing, BLAKE3, sanitize, registry — zéro I/O, zéro UI
│   ├── droplink-net/           # mDNS, TCP, relay client — tokio pur, testable en loopback
│   ├── droplink-app/           # binaire UI
│   └── droplink-relay/         # serveur (déplacé dans le workspace)
├── benches/                    # criterion : framing, checksum, throughput loopback
└── tests/                      # intégration : deux nœuds, transfert réel, rejet, checksum corrompu
```

Gains attendus : cœur 100 % testable sans GUI, `cargo test` en secondes, benchmarks reproductibles, binaire unique,
0 dépendance Node si l'UI passe en Rust natif.

Les décisions structurantes (UI native vs Tauri, sort du relay) sont tranchées avant d'écrire le blueprint.
